## Gaps (plan vs. pinned reality — read carefully, these bound what "done" means this phase)

1. **Fence language never reaches `Decor::highlight`.** `crates/layout` discards `BlockKind::CodeBlock`'s `info` string, and `Painter::paint_runs` hardcodes `lang: None`. Both are P4/P5, already committed, outside this phase's file scope (`crates/layout/**`, `crates/stele/src/painter.rs` are not in my scope). **Consequence:** as the app is wired *today*, no code block will show per-language colors — `highlight_line(text, None)` always degrades to plain, identically to the old `StructuralDecor`. This phase's `Decor`/`Theme`/`highlight_line` are built and tested to be fully correct *given* a real `lang` (verified directly, bypassing `Painter`); closing the gap needs a `Run`/`Line` schema change in `crates/layout` plus a `Painter::paint_runs` change to actually pass the block's language through — both out of scope here. Flagged for the orchestrator/a follow-up phase, not silently absorbed.
2. **No URL or footnote-label channel reaches `Run`/`Style`.** `Decor::resolve(StyleId) -> Style` never sees run text, and `Style` (painter.rs, pinned) has no hyperlink field; `Decor::highlight` only fires for `CodeBlock` runs, never `Link`/`FootnoteRef`. **Consequence:** real OSC 8 emission end-to-end through `Painter::frame` is not reachable from inside this phase's scope. What *is* delivered: a fully correct, independently tested URL-sanitization + OSC 8 sequence-building module (`crates/highlight::hyperlink`) and a footnote-anchor module (`crates/highlight::footnote`), satisfying DW-7.4/DW-7.6's literal wording ("emission assertion" — tested directly, not via a live `Painter::frame` capture) and ready for a future seam change to wire through.
3. **Mermaid rendering reshapes text (different line/column count than the source), which the Constraints section forbids `Decor::highlight` from doing** ("a pure run transformation that cannot change layout ... only the run partitioning and styles change"). Mermaid therefore cannot be a `Decor::highlight` responsibility at all. **Resolution:** `crates/mermaid` is a standalone source-text transform (render a ` ```mermaid ` fence body, replace it in the raw markdown *before* `Document::parse`) — a preprocessing pass at the same conceptual layer as frontmatter-hiding, exposed as a public function for the orchestrator to call in `main.rs` (one more line, alongside `register_decor`), not wired through `Decor`.
4. **Frontmatter hiding cannot happen via `Decor`** (no channel to suppress a run's text, only its style). **Resolution:** `crates/stele/src/decor::frontmatter::apply(source, show)` strips the leading `---`-fenced block from the raw source text before parsing when `show` is `false` — same shape as (3).
5. **Adding new fixtures broke an already-anchored P4 test** (`crates/layout/tests/dw.rs`'s golden-snapshot test auto-discovers every `fixtures/*.md`). Fixed via the test's own documented, sanctioned mechanism (`UPDATE_LAYOUT_GOLDENS=1 cargo test -p layout`), which only **added** two new golden files (`hostile-links.*`, `mermaid.*`) — verified via `git status` that no existing golden was modified.

None of these gaps are silent: each is a deliberate, documented boundary decision, not a redesign of a pinned seam. No DW item was CANNOT_MEET as a result — see DW Verification below for exactly how each was satisfied within scope.

## Design Decisions

**Crate boundary (`crates/highlight` cannot depend on `stele`).** `crates/highlight` defines its own `Color`/`Style` types, field-for-field identical in shape to `crates/stele/src/painter`'s, rather than depending on `stele` (which depends on `highlight` via `decor`). `crates/stele/src/decor/themed.rs::bridge_style`/`bridge_color` are the (trivial, copy-only) translation. Chosen over the alternative of putting `Theme` inside `crates/stele` directly, because the plan's file scope and "Produces" line both name `crates/highlight: Theme::resolve(&self, id: StyleId) -> Style` as a standalone crate deliverable.

**Capture-role collapsing (`crates/highlight::role::Capture`, 25 variants incl. `Plain`).** lumis emits ~293 dot-hierarchical scope names; mapping each to its own `StyleId::Capture` would make the DW-7.2 "distinct color per role" guarantee both enormous and pointless (most of those 293 names are per-language specializations of a much smaller semantic vocabulary — `"keyword.import.rust"`/`"keyword.import.go"` should look the same). `Capture::from_scope` prefix-matches the dot-hierarchy down to ~24 real syntactic roles (keyword, function, type, string, comment, ...) plus `Plain` for anything unrecognized. Chosen over a 1:1 scope→id mapping (293 colors is neither reviewable nor guaranteed distinct after 256-color downsampling) and over a hand-picked handful of "most common" scopes (silently misclassifies everything else instead of degrading safely to `Plain`).

**Palette generation: greedy-distinct construction, not a formula (`crates/highlight/src/theme.rs::build_palette`).** First attempt was a pure golden-angle hue rotation at one fixed saturation/lightness per variant — this collided under 256-color downsampling (verified: role 11, then role 19, collided in successive attempts) because a single hue ring, quantized to xterm's 6 steps/channel, does not reliably carry 44 distinct cells. Final design: `build_palette` greedily walks hue-rotated candidates across 5 saturation/lightness "bands," rejecting any candidate whose *downsampled* value collides with an already-accepted role, so distinctness is guaranteed by construction (and verified) rather than hoped-for from a formula. The palette is built once at `Theme::new` (not per `resolve` call — `resolve` runs on every painted run, every frame).

**Per-line highlighting: verified compatible, with a documented residual limitation (Assumption Verification).** Read lumis 0.12.0's actual source (`highlight_iter`, `Language::guess`): it genuinely accepts a single line and returns raw `(text, scope, style)` spans with `theme: None`, so it *can* satisfy the pinned per-line `Decor::highlight` contract. What it cannot do correctly per-line: any construct spanning multiple lines (block comments, multi-line strings) — each `highlight_line` call re-parses from scratch with no memory of the previous line. This is documented in `crates/highlight/src/highlighter.rs`'s module doc and pinned by `test_multiline_comment_construct_is_a_known_limitation` (asserts no panic/no text loss, explicitly not "correct" multi-line classification) rather than silently shipping wrong-looking output with no record of why.

**Highlight time cap: size-gated, not always-threaded.** First attempt spawned a background thread + `recv_timeout` for every single line — this was flaky under `cargo test`'s parallel test execution (thread-scheduling contention pushed even trivial one-line highlights past a 150ms cap). Fixed by only paying the thread-spawn cost above `THREADED_GUARD_THRESHOLD` (4096 bytes) — every realistic source line runs inline with no overhead; only a suspiciously large line gets the real wall-clock-bounded guard, satisfying the Constraints section's "must hit a time cap and degrade to plain rather than hanging" without flaking on ordinary input.

**Mermaid and frontmatter-hiding as source-text preprocessing, not `Decor` methods.** Both need to change *what a block's rendered content is* before layout, which the pinned `Decor` interface (post-layout, per-run, text-preserving) cannot do (see Gaps 3–4). Both are exposed as plain functions (`mermaid::render`/`render_ascii_verified`, `stele::decor::frontmatter::apply`) for the orchestrator to call before `Document::parse`, mirroring how `--max-width`/`--no-images`/`--frontmatter` were already "parsed here, consumed elsewhere" in P5's own design note in `cli.rs`.

**`mermaid-text`'s ASCII-purity gap: fixed with a second substitution pass, not re-asserted.** Per the carried-forward gotcha, `render_ascii_verified` calls upstream's `render_ascii()` then re-scans for any remaining non-ASCII character, substituting the two diagonal box-drawing glyphs (`╱`/`╲`) the spike found missing from upstream's own table (plus `╳` for the same shape family), and `?` for anything else unrecognized — so its ASCII guarantee is checked, not copied from a doctest that the spike proved false.

**OSC 8 barricade: allowlist-then-strip, re-validated after stripping.** `sanitize_url` checks the scheme twice — once on the raw URL (fast rejection of `javascript:`/`data:`), and again on the *stripped* string (catches a scheme hidden behind embedded control bytes, e.g. `h<ESC>ttp://...`, which would otherwise pass the first check as garbage and only "become" `http` after stripping). This directly targets the reviewer's stated concern ("a prior phase shipped a security test whose whitelist was looser than advertised") — `test_dw_7_6_scheme_hidden_behind_control_bytes_is_still_rejected` and the byte-level (not substring-level) scan in `test_dw_7_6_embedded_control_bytes_never_reach_the_sequence` are the direct response.
