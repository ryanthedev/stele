## Gaps

- Phase brief's Produces list names `ImageSizer: IntrinsicSizer` as a single type, but Scope IN requires sizing for both images (header probe) and math (so math ever gets a `Reserved` box instead of permanently falling back to literal TeX). Resolved via the layout crate's own doc comment (see above) — one sizer, two node kinds.
- `math::render`'s pinned signature is `(tex: &str, px_height: u32) -> Result<Png, MathError>` — no color parameter, yet `ratex.md`'s hard consequence is "never rely on `LayoutOptions::default()`". Resolved by hardcoding an explicit light ink color inside `render()` (documented deviation: P6 has no live theme color yet — P7 owns that layer per the plan's own Decision Log — so an explicit constant is the correct, honest interim choice, still satisfying "never default black").
- `ratex-parser::parser::parse` per the spike doc's paraphrase is actually `ratex_parser::parse` (re-exported at crate root, not nested under a `parser` module) — verified by reading the real source; used the real signature, not the spike's paraphrase.
- `ratex_layout::layout`/`to_display_list` produce a `DisplayList` carrying em-unit `width`/`height`/`depth` — this is what makes a genuinely cheap (non-rasterizing) size probe for math possible, mirroring the header-only spirit of the image probe without literally reading a "header."

## Design Decisions

**Crate boundaries.** `crates/gfx` owns the kitty graphics protocol (`Emitter::{transmit,place,delete}`, `ImageId`, its own `CellRect`) *and* image decode/header-probe (`decode` module, using the `image` crate with `Limits`) — the phase goal statement groups "owned kitty graphics emission, adopted decode" together, and keeping decode next to emission means one crate owns "how a raster of known pixel dimensions gets onto the Ghostty screen," independent of what produced those pixels (a decoded photo or a RaTeX PNG). `crates/math` owns RaTeX + txm + the literal-source ladder's data (`render`, `render_text`, `Png`, `TextGrid`, `MathError`). `ImageSizer` and the `MediaSink` impl (`GfxMediaSink`) live in `crates/stele/src/media/` since they are the integration point needing `ast`+`layout` (which neither `gfx` nor `math` depend on) plus both `gfx` and `math`.

**One sizer, two node kinds.** `ImageSizer` implements `IntrinsicSizer` for both `InlineKind::Image` (header-only probe via `gfx::decode::probe_dimensions`) and `InlineKind::Math` (a genuinely cheap, non-rasterizing probe: RaTeX parse+layout+`to_display_list` gives em-unit `width`/`height` directly — no `render_to_png` call, so no pixels are ever produced at layout time, mirroring the "no full decode at layout time" spirit for the image path). If RaTeX parsing fails, `ImageSizer` falls back to trying `txm::layout` for a plain cell grid size before giving up (returning `None`, which degrades to the existing literal-TeX `Semantic::MathTex` alt-text path already built and tested in P4/P5) — this makes the txm rung also get a real `Reserved` box instead of always bottoming out at literal text.

**Math ink color.** `math::render` never uses `LayoutOptions::default()` (which is `Color::BLACK`, measured at 1.24:1 contrast on Ghostty's dark theme per `ratex.md`). It hardcodes an explicit light color (`Color::new(0.9, 0.9, 0.9, 1.0)`) and a transparent background (`Color::new(1.0, 1.0, 1.0, 0.0)`), per the spike's own measured-safe recipe. **Documented limitation:** this is a static choice, not a live theme lookup — P6 has no OSC-10/11-resolved foreground color available (that lands with P7's theme engine per the plan's own Decision Log, "P5 paints structural styles only; theme engine lands in P7"). This satisfies the letter and spirit of the spike's consequence (never default black) while being honest that full theme integration is future work.

**Caching (DW-6.5).** `crates/math` maintains two bounded, capacity-256, insertion-order-evicted caches behind `std::sync::Mutex`: a `DisplayList` cache keyed by the exact TeX source string (skips re-parse+re-layout on a `px_height`-only change), and a final-PNG cache keyed by `(tex, px_height)` (skips re-rasterization entirely on an unchanged request). A `cache_stats()` function exposes hit/miss counters so DW-6.5 is asserted deterministically (call-count introspection) rather than via timing, which would be flaky. Separately, at the `MediaSink` level: `GfxMediaSink::paint`/`evict` take no `&Document`/`&WidthEngine` — by construction the sink cannot call `layout::layout()` even in principle, which is the strongest possible proof that a cell-geometry change can never trigger a document re-layout from this code path.

**Placement mode — deviation from the plan's stated primary.** `docs/spikes/ghostty-caps.md` item 3: virtual placement `U=1` is "accepted at the sequence level — visual placement not independently confirmed," and explicitly instructs *"P6 should budget one manual visual pass before treating virtual placement as load-bearing... if that visual pass fails, fall back to direct placement + repaint-behind."* No manual visual pass has been run in this build (no interactive GUI session available in this environment — see Prerequisites). Per the phase's own Assumption Verification instructions ("If the verdict does not support virtual placement, use direct placement + repaint-behind and record the deviation — do NOT claim a capability the spike didn't confirm"), **`Emitter` implements direct placement + repaint-behind, not `U=1` + Unicode placeholders.** `Emitter::place` moves the cursor to `rect.x,rect.y` via `CSI row;colH` then emits `a=p,i=<id>,c=<cols>,r=<rows>` (put an already-transmitted image at the cursor, sized in cells) rather than emitting `U=1` transmission + placeholder codepoints elsewhere. This is a genuine scope deviation from the phase body's stated primary mode, made honestly per the phase's own explicit fallback instructions rather than silently claimed as the verified path.

**Eviction / "one-viewport margin."** The `MediaSink` trait (pinned by P5) gives `paint`/`evict` no scroll-position or viewport-height parameter — only `Reserved` + `CellRect` per visible row, called in ascending-row order once per `Painter::frame` call. `GfxMediaSink` infers frame boundaries from this call pattern (a `rect.y` that is `<=` the previous call's `y` starts a new frame) and evicts a node only after it has been absent for one full frame beyond visibility (a one-frame grace period) — the closest achievable analog to "one-viewport margin" given the trait's actual inputs. This is a bookkeeping/implementation-detail choice, not a change to any DW-pinned deliverable; documented here rather than silently assumed. The LRU cap of 32 live placements is enforced independently of the margin logic: the 33rd distinct live node evicts the least-recently-painted node first.

**Alt-text/no-graphics barricade.** DW-6.4 is satisfied structurally, not by a runtime branch inside `paint()`: `ImageSizer::new(.., disabled: bool)` with `disabled=true` (the caller sets this from `$TMUX`/`--no-images`/a failed capability probe) makes `size()` always return `None` for every node, so `layout::layout()` never emits a `Reserved` line for any image/math node — the document falls back through the already-tested P4/P5 path (`Semantic::ImageAlt`/`Semantic::MathTex` runs through `Painter::frame`'s ordinary sanitized text path). Since `MediaSink::paint` is then never invoked at all in that mode, "zero graphics escapes" holds by construction rather than by a sink-side check that could be forgotten. This also means the *orchestrator's* one-line integration is genuinely one decision: which sizer to construct, not two independent flags to keep in sync.

**Any text `MediaSink` writes directly must be sanitized independently of `Painter`.** `painter.rs`'s `sanitize` function is private and out of my file scope to touch. When `GfxMediaSink` degrades to alt-text (a real decode/render failure discovered *after* a `Reserved` box already exists — e.g., the file was deleted between layout and paint) it writes plain text directly to `out`, bypassing `Painter`'s barricade. A small equivalent C0/C1/DEL stripping helper is duplicated locally in `crates/stele/src/media/sink.rs`, documented as a deliberate, minimal duplication forced by the file-scope boundary rather than an oversight.

**Hostile image fixtures.** Authored programmatically inside `crates/gfx/src/decode.rs`'s test module (not committed binary files) — a hand-built minimal PNG signature + `IHDR` claiming a bomb dimension (`50000x50000`) with no further chunks, a truncated real PNG (valid signature, `IHDR` cut off mid-chunk), and garbage bytes with a spoofed JPEG magic number. Building them in Rust keeps them auditable and avoids adding binary fixtures outside my file scope.
