## Design Decisions

**Launch pattern (had to be discovered, not assumed).** The dispatch brief's own suggested pattern — `ghostty -e <probe-binary>` as a direct exec of the `ghostty` CLI binary — was tested first, per the brief's own instruction to "verify this launch pattern early." It hangs indefinitely: confirmed three separate ways (foreground with a 15s `timeout`, backgrounded with `nohup`, and via `launchctl asuser $(id -u) ghostty -e ...`), all leaving the invoking process alive but stuck before ever exec'ing the child. The working pattern goes through macOS's `open(1)`: `open -na /Applications/Ghostty.app --args -e <bin> <args...>`. This was verified incrementally (trivial shell echo → the real `spike_a` binary) before being built into `crates/probe::Launcher`. Recorded in `docs/spikes/ghostty-caps.md` so a later phase doesn't re-burn the same debugging cycle.

**`GhosttyPty` as the barricade (cc-defensive-programming).** The crate's one external-input boundary is "is this process actually attached to a Ghostty-hosted PTY," and it's validated once, at construction (`GhosttyPty::from_current_process`: `isatty` on fd 0/1 plus `TERM_PROGRAM == "ghostty"`), producing a token type with no public constructor that skips the check. Every `Probe::open` is therefore built from a validated environment — matching the skill's barricade design ("validate at the external boundary... assume validated data inside").

**Timeout defense is layered, not single-point.** Three independent layers, each independently tested: (1) `io_raw::poll_readable` bounds every single read with `poll(2)` before ever calling `read`, so no syscall can block past its budget; (2) `Probe::query`'s quiet-window logic (`read_until_quiet`) bounds a multi-chunk response's *total* wait by the caller's `timeout`, never re-arming it; (3) `Launcher::run_probe` bounds the *whole external Ghostty launch* by its own `timeout`, independent of whatever the probe binary does internally. This directly answers the plan's stated edge case ("probe read timeouts — a non-answering terminal must not hang the harness") at every layer where a hang could originate, not just the innermost one.

**Pinned signatures implemented literally, including their awkward parts.** The plan pins `Probe::open(GhosttyPty) -> Probe` (no `Result`) and `cursor_pos(&mut self) -> (u16, u16)` / `measured_width(&mut self, s: &str) -> u16` (no `Option`). Both were implemented exactly as pinned rather than silently redesigning the seam: `Probe::open` `.expect()`s on a raw-mode-enable failure (justified — `GhosttyPty` already proved stdio is a real tty, so failure past that point is an environment fault a probe binary can't usefully recover from, not an anticipated condition); `cursor_pos`/`measured_width` fall back to a documented `(0, 0)` / `0` sentinel on the internal ~800ms timeout, with the doc comment explicitly telling callers that need to distinguish "really at (0,0)" from "no reply" to call `query` directly. This is a recorded interface constraint, not a silent gap — P3/P5/P6 build against exactly this behavior.

**Test-only fd-pair constructor, not test-only trait indirection.** `Probe::from_raw_fds_for_test` (`#[doc(hidden)] pub`) exists so the CI-safe `pty_pipeline.rs` tests can exercise the real `query`/`cursor_pos`/`measured_width` code paths over a real POSIX pty pair, without needing to fake stdio or introduce a trait-object abstraction over the fd layer purely for testability. Kept `pub` (not `pub(crate)`) because integration tests in `tests/` compile as a separate crate against `probe`'s public API only — `#[doc(hidden)]` communicates "not part of the supported surface" without actually restricting visibility, which was necessary once the timeout tests needed to live in `tests/` (not inline `#[cfg(test)]`) to avoid conflating "pure logic tests" with "tests that spin up a real pty and a background thread."

**Spike B/C delegated to parallel subagents; Spike A run directly.** Spikes B (highlight engine, Mermaid) and C (RaTeX corpus) don't depend on the local Ghostty-launch capability this session had to establish, and are independently large empirical tasks (real crate builds, a real `git clone` + test-suite run). They were dispatched as background research/build agents with grounded, pre-verified crate names and repository URLs (looked up via the crates.io API before dispatch, to avoid the agents rediscovering — or worse, guessing — them), explicit instructions to write only the single target doc file, and an explicit instruction to report "could not measure" honestly rather than extrapolate. Both returned real, independently-verifiable measurements (exact byte counts, exact pass/fail counts, exact pixel/contrast values) and both surfaced genuine, unprompted findings beyond the letter of their brief (lumis's `Language::SQL` naming mismatch; `mermaid-text`'s `render_ascii()` ASCII-purity claim being empirically false for decision-node diagrams; RaTeX's own CI font-path bug). Spike A was run directly in this session because it required the just-discovered live-Ghostty launch pattern, which existed only in this session's context.
