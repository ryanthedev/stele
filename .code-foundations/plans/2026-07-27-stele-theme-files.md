# Plan: stele theme files — shareable, user-authored colors
**Created:** 2026-07-27
**Status:** complete
**Completed:** 2026-07-27
**Complexity:** medium
**Review cadence:** 2
---
## Context

stele's colors are compiled in. Two built-in `Variant`s, a palette generated by `build_palette`'s golden-angle walk, `HEADING_RAMP` as the only hand-picked colors, and no way to change any of it without editing Rust and rebuilding. The previous plan made this an explicit non-goal (`2026-07-25-stele-viewer-features.md` line 21: "No user theme files — the theme toggle switches between the two built-in variants only"). That call is now reversed.

The goal is themes as **shareable artifacts**: one self-contained file is one theme. You download someone's, save it, and stele uses it. Runtime switching between installed themes is explicitly *not* required — the user's words: "not a requirement. I can restart with a new theme." That removes a theme picker, a themes-directory scan, and any redefinition of the `T` key's meaning.

Body prose must become colorable. Today `Semantic::Text`, `Strong`, `Emph`, `Strikethrough`, `CodeBlock`, and `MathTex` return `None` from `semantic_role_index` and inherit the terminal's default foreground. That default is deliberate and stays — a theme file is what overrides it.

## Constraints

- **`Theme::resolve` stays total.** A malformed, partial, hostile, or absent theme file must never panic and must never leave a role unresolvable.
- **Theme files are untrusted input.** Parsed with a real parser, never hand-split. No value from a theme file may reach the terminal as an escape sequence — a second untrusted path alongside document text, which already has the sanitization barricade.
- **The built-in variants keep every invariant they have now**: heading rungs clear WCAG AA against the reference backgrounds, every colored role stays distinct after 256-downsampling, and the H1 wash never costs the title its contrast. A *user* theme may violate these; the built-ins may not.
- **No wildcard arms over `Semantic`.** Adding a role must stay a compile error until the name table names it too — the discipline that already protects the style tables, extended to the table that names them.
- **No default rendering changes with no theme file present.** Same colors, same keys, same auto-detect, same `NO_COLOR` behavior.
- **No capture role repaints.** The overlay must not shift palette indices; `test_capture_colors_are_pinned_so_a_new_role_cannot_silently_restyle_code_blocks` must pass untouched.
- Dependency direction stays one-way; nothing may depend on `stele`. Theme parsing belongs in `highlight` (it owns `Theme`); file discovery belongs in `stele`.
- `#![forbid(unsafe_code)]` holds. Conventions in `docs/code-standards.md` apply — exhaustive matches, hand-rolled error enums, sentence-style test names, DW-tagged tests.

## Chosen Approach

**A sparse overlay consulted ahead of the generated palette.** A parsed theme file produces `ThemeOverrides` — a role→color map that is empty for anything the file omits. `Theme` carries an `Option<ThemeOverrides>`; `resolve_semantic` checks it first and falls back to `semantic_role_index` → `color_for` exactly as today.

**Rationale:** three properties fall out for free rather than being engineered.

1. **Partial themes cost nothing.** An absent key is an absent map entry is the built-in color. A five-line theme is valid without a merge algorithm.
2. **No palette churn, so no repaints.** `build_palette`, `SEMANTIC_ROLES`, and every index stay exactly as they are. The overlay is a lookup *in front of* the palette, not a change *to* it.
3. **Colorless roles become colorable without becoming colored.** `Semantic::Text` still returns `None` from `semantic_role_index`, so with no theme file body prose still inherits the terminal foreground. With a theme file that names `text`, the overlay answers before the palette is ever consulted. No new palette slot, no default change.

**Fallback:** if the overlay lookup ever shows up in a frame profile (it is one map probe per run, on a path that already does an index lookup), swap the map for a `[Option<Color>; role_count()]` array indexed by the same role index — a mechanical change behind the same API.

## Rejected Approaches

- **Replace `build_palette` with an explicit color table.** Makes every color nameable and a theme file the single source of truth. Rejected: it forces every theme to specify all ~30 roles or invent a merge layer anyway, throws away the golden-angle generator's 256-distinctness guarantee, and repaints every capture color again — the exact churn we just absorbed once and do not want to re-inflict.
- **A parallel `UserTheme` type alongside `Theme`.** Cleaner separation on paper. Rejected: it duplicates `resolve` and gives the painter two code paths to keep in sync, and every invariant test would need running twice against two types that must not drift.
- **Give the colorless roles real palette slots at `TRAILING_ROLE_BASE`.** The comment at `SEMANTIC_ROLES` explicitly blesses appending there. Rejected: appending is index-inert but *not* render-inert — the roles would pick up generated colors and body prose would become colored by default, which is a rendering change for every user who has no theme file.

## Implementation Phases

### Phase 1: Public role names and the overlay seam
**Model:** fable
**Skills:** code-foundations:aposd-designing-deep-modules, code-foundations:code-clarity-and-docs
**Gate:** Full
**Depends on:** none
**File scope:** crates/highlight/src/theme.rs, crates/highlight/src/lib.rs, crates/layout/src/lib.rs

**Goal:** Give every `Semantic` role a stable public name, and give `Theme` an overlay that answers ahead of the generated palette.

**Scope:**
- IN: a bidirectional, exhaustive name table (`role_name(Semantic) -> &'static str`, `semantic_from_name(&str) -> Option<Semantic>`) with the no-wildcard guard extended to it; `ThemeOverrides` as a sparse role→color map; `Theme::with_overrides`; `resolve_semantic` consulting the overlay before `semantic_role_index`; names for the heading rungs (`heading1`..`heading6`) and the alert tones (`alert_note`..`alert_caution`).
- OUT: any file format, any parsing, any I/O, any CLI. This phase is reachable only from Rust.
- OUT: naming `Capture` roles, `HeadingRung`, `SearchMatch`/`SearchCurrent` — captures are out of scope per the coverage decision, and `HeadingRung` is an internal spelling of `Heading` that must not be separately themeable.

**Edge cases:** A name that round-trips to a different role than it came from (guard with a round-trip test over every role). An overlay entry for a role that resolves to `None` today — must produce a color, since that is the body-prose requirement. An overlay entry under `NO_COLOR` — must be ignored, because a theme file is a color and `NO_COLOR` means no colors. `Heading(0)` and `Heading(7)` must clamp to a real name rather than panic or produce a name no file can contain.

**Produces:**
- `highlight::role_name(layout::Semantic) -> Option<&'static str>` — `None` for roles deliberately not themeable, so the caller cannot accidentally expose one.
- `highlight::semantic_from_name(&str) -> Option<layout::Semantic>`
- `highlight::ThemeOverrides` — constructed from `IntoIterator<Item = (Semantic, Color)>`, queried by `Semantic`.
- `highlight::Theme::with_overrides(Variant, ColorMode, ThemeOverrides) -> Theme`
- `highlight::THEMEABLE_ROLES: &[&str]` — every valid name, for error messages and docs.

**Done when:**
- [ ] DW-1.1: `role_name` and `semantic_from_name` round-trip for every themeable role, proven by a test that enumerates them from `THEMEABLE_ROLES` rather than a hand-written list.
- [ ] DW-1.2: Adding a `Semantic` variant is a compile error in the name table (no wildcard arm), verified the way the existing guards are — an exhaustive `match` with no `_`.
- [ ] DW-1.3: `Theme::with_overrides` colors `Semantic::Text`, which resolves to `None` without an overlay, proving a colorless role is overridable without becoming colored by default.
- [ ] DW-1.4: A `Theme` with an empty overlay resolves every role identically to `Theme::new` — the overlay is inert when unused.
- [ ] DW-1.5: `test_capture_colors_are_pinned_so_a_new_role_cannot_silently_restyle_code_blocks` passes unmodified.
- [ ] DW-1.6: Under `ColorMode::NoColor`, an overlay naming every role still resolves every role to no foreground.

### Phase 2: The theme file format, parser, and validation
**Model:** fable
**Skills:** code-foundations:cc-defensive-programming, code-foundations:aposd-verifying-correctness
**Gate:** Full
**Depends on:** Phase 1
**File scope:** crates/highlight/src/theme_file.rs, crates/highlight/src/lib.rs, crates/highlight/Cargo.toml

**Goal:** Parse a TOML theme file into `ThemeOverrides` plus a list of warnings, never failing in a way that costs the user their document.

**Scope:**
- IN: the TOML schema (`name`, `appearance`, and a `[colors]` table of role name → hex string); `serde` + `toml` dependencies on `highlight`; hex parsing (`#rrggbb` and `#rgb`); a hand-rolled error/warning enum per the codebase's convention; validation that collects *every* problem rather than stopping at the first; the AA and 256-distinctness checks run against a user theme to produce warnings, reusing the same arithmetic the built-in tests use.
- OUT: reading files from disk, path resolution, environment, CLI — Phase 3 owns all I/O. This phase's entry point takes `&str`.
- OUT: writing or serializing themes. Read-only.

**Edge cases:** Unknown role name (warn, name the closest valid role, continue). Malformed hex (warn, skip that role, continue). Wrong TOML type — a number where a string belongs (warn, skip, continue). Missing `appearance` (default to `dark`, warn). Unparseable TOML at the top level (this is the one hard failure — there are no overrides to salvage; return an error and let Phase 3 fall back to the built-in). Empty `[colors]` table (valid; yields an empty overlay). A theme whose colors put heading text under AA or collide after 256-downsampling (warn, honor anyway — the user's explicit choice). Escape sequences, control characters, or C1 bytes anywhere in the file (must never reach the terminal; the only values that leave this module are parsed `Color`s and warning text this module itself composes).

**Produces:**
- `highlight::ThemeFile { name: String, appearance: Variant, overrides: ThemeOverrides }`
- `highlight::ThemeFile::parse(&str) -> Result<(ThemeFile, Vec<ThemeWarning>), ThemeError>` — warnings ride alongside a successful parse; `ThemeError` is only for a document with nothing salvageable.
- `highlight::ThemeWarning` with a `Display` that names the role and the problem in one line fit for the status row.
- `highlight::ThemeFile::lint(&self, ColorMode) -> Vec<ThemeWarning>` — the AA and distinctness checks, separated from parsing so a caller can skip them.

**Security-sensitive:** yes — this is deserialization of an untrusted file, and it is the second path by which non-document bytes could reach the terminal.

**Done when:**
- [ ] DW-2.1: A five-line theme naming only `text` parses to an overlay of exactly one role, with no warnings.
- [ ] DW-2.2: Every documented failure mode — unknown role, bad hex, wrong type, missing appearance — yields a warning naming the offending key and leaves every *other* role in the file applied.
- [ ] DW-2.3: A theme file containing ESC, C0, or C1 bytes in any string field produces no escape sequence in any `ThemeWarning`'s `Display` output, asserted byte-wise.
- [ ] DW-2.4: A theme that puts a heading under WCAG AA parses successfully, and `lint` reports it.
- [ ] DW-2.5: Malformed TOML returns `ThemeError` rather than panicking, for at least: unclosed string, unclosed table header, invalid UTF-8 handled upstream, and a 1 MB pathological input.
- [ ] DW-2.6: Parsing is a pure function of its `&str` input — no environment reads, no file access — verified by the module having no `std::fs` or `std::env` import.

### Phase 3: Discovery, CLI wiring, and surfaced warnings
**Model:** sonnet
**Skills:** code-foundations:cc-defensive-programming, code-foundations:cc-routine-and-class-design
**Gate:** Standard
**Depends on:** Phase 2
**File scope:** crates/stele/src/cli.rs, crates/stele/src/main.rs, crates/stele/src/decor/themed.rs, crates/stele/src/theme_source.rs, crates/stele/tests/theme_file.rs

**Goal:** Find a theme file, load it, and tell the user in the status line when something was wrong with it.

**Scope:**
- IN: `--theme <path>`; the default path `~/.config/stele/theme.toml` honoring `XDG_CONFIG_HOME`; precedence (flag beats config path beats built-in); the interaction with OSC 11 auto-detect (a theme's declared `appearance` selects which built-in it overlays, and a mismatch against the detected terminal background warns); `T` behavior with a user theme active (toggles between the user theme and the built-in of the opposite appearance); warnings routed to the existing status-message channel; `NO_COLOR` still wins over everything.
- OUT: any change to the parse/validate logic — Phase 2 owns it.
- OUT: watching the theme file for changes, reloading it at runtime, a picker overlay. Explicitly dropped: switching themes means restarting.

**Edge cases:** `--theme` pointing at a missing file (hard error at startup with a clear message — the user named it explicitly, so silence would be wrong). Default config path missing (silent, the overwhelmingly common case). Theme file unreadable due to permissions (warn, use built-in). `$HOME` unset (skip the default path, do not panic). A theme file that is a directory. `--theme` combined with `NO_COLOR` (theme parses, colors are ignored, and the status line says so rather than looking broken). More warnings than fit the status row (show a count and the first, not a truncated wall).

**Produces:** `stele::theme_source::resolve_theme(cli_path: Option<&Path>, bg_reply: Option<&[u8]>) -> (highlight::Theme, Vec<ThemeWarning>)` — the single seam `main.rs` and the `T` handler both call.

**Done when:**
- [ ] DW-3.1: `stele --theme <file>` renders the document with that file's colors, verified through the pty harness by asserting the emitted SGR bytes, not by inspecting the `Theme` struct.
- [ ] DW-3.2: With no theme file anywhere and no flag, every emitted byte is identical to the current build — the no-config path is unchanged, verified against a golden frame.
- [ ] DW-3.3: `--theme` at a missing path exits non-zero with a message naming the path; a missing *default* config path is silent.
- [ ] DW-3.4: A theme with warnings still renders the document, and the first warning appears in the status row.
- [ ] DW-3.5: `NO_COLOR=1` with a theme file emits no color escapes at all.
- [ ] DW-3.6: `T` with a user theme active swaps to the built-in of the opposite appearance and back, preserving the scroll anchor like every other relayout.

## Notes
- The overlay is checked *before* `semantic_role_index`, which is what makes a colorless role overridable. Reversing that order would silently break the body-prose requirement while every other test still passed.
- `Semantic::HeadingRung` must not be themeable. It is an internal spelling of `Heading`'s rung color introduced by `104e8a9`; exposing it would let a theme desynchronize a heading from its own markers.
- The AA and 256-distinctness checks become *warnings* for user themes while staying *hard test failures* for the built-ins. The arithmetic should be shared so the two cannot drift.
- `docs/code-standards.md` is 17 commits stale as of this plan (last touched `d92e280`). Worth regenerating, but it is not a dependency of this work.

## Execution Log

**2026-07-27 - all four phases shipped. 748 tests passing, clippy and fmt clean.**

Two deviations from the plan as written, both deliberate:

- **`search_match` / `search_current` are themeable.** The plan put them OUT of
  Phase 1's scope. That was arbitrary - they are ordinary semantic roles with
  palette slots, and a shared theme that cannot set the search highlight is an
  odd gap. Included, and `docs/theming.md` lists them.
- **DW-4.1's "zero unintended warnings" resolved as contrast-only.** The
  shipped themes are asserted free of *contrast* failures, and their
  256-colour collisions are documented in each file rather than eliminated.
  This is not a shortcut: the xterm cube offers six steps per channel - 216
  colours, six of them grey - so a palette coherent enough to read as one
  theme cannot also be 33-ways distinct after quantization. `build_palette`
  only achieves it for the built-ins by *generating* colours through a dedup
  loop, which is exactly why its own heading ramp had to be hand-picked and
  exempted. A low-saturation theme like `lichen` is competing for six cells.

Three findings worth recording:

- **The lint's first collision rule was wrong.** It flagged roles the author
  had deliberately painted the same colour (`link` and `alert_note` sharing one
  blue). Now only colours that *differ* in truecolor and then merge are
  reported - the actual surprise.
- **One contrast floor was wrong.** Holding a rule glyph to WCAG 1.4.3's 4.5:1
  forces every theme to paint its furniture as loudly as its prose. Structural
  roles now answer to 1.4.11's 3:1, via an exhaustive `is_structural`.
- **Fading a heading ramp toward the page walks its deep end under AA.** The
  first `ember` draft put H6 at 2.5:1 - the same regression the built-in ramp
  was rebuilt to fix. All three ramps now fade by *saturation* at a roughly
  constant contrast.

Summary: `Semantic` gained public names and a `ThemeOverrides` overlay
consulted ahead of the generated palette (so colourless roles like `text`
became settable without becoming coloured by default, and no capture role
repainted); `highlight::theme_file` parses a TOML theme with no I/O and
collects warnings rather than failing; `stele::theme_source` owns discovery,
`--theme`, the config path, and what `T` means with a theme loaded; three
complete themes and `docs/theming.md` ship, with a test that keeps the doc's
role list from rotting away from `THEMEABLE_ROLES`.
